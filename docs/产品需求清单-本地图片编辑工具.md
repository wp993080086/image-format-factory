# 产品需求清单｜本地图片编辑工具

> 版本：**v0.9**（2026-11-25 需求池新增「拼图与九宫格」三组需求：朋友圈拼图、九宫格切图、裸眼 3D 九宫格）
> 定位：**纯本地离线图片处理**，原图不上传服务器；多端部署：Windows / Android / HarmonyOS Next，后续拓展微信小程序
> 核心规则：各端能力不一致，**功能按端做差异化阉割**；优先保障 PNG 透明通道保留；JPG 原生不支持透明，转换时界面提示用户
> 选型背景备忘：Flutter 为主基线，小程序单独适配、能力最弱
> **端优先级**：Windows（首发基线）→ **HarmonyOS Next（优先级高于 Android）** → Android → 微信小程序
> **MVP 端范围（已拍板）**：Windows + HarmonyOS Next + Android **三端同步**；微信小程序延后至 V3+（附录 #7 / #11 已拍板）

## 一、支持图片格式（导入 / 导出分开，区分【导入支持】、【导出支持】）

> 说明：下面是通用全集；每个端单独维护一张兼容表，不支持的格式在对应端隐藏选项、置灰

### 导入（可打开预览、进入编辑）

- 位图类：JPEG（jpg/jpeg）、PNG、BMP、WebP、**TIFF / TIF（v0.5 拉回）**
- 动图类：GIF、APNG、**动图 WebP**
- 矢量类：SVG
- 图标类：ICO
- **手机相册格式（v0.3 新增）**：HEIC / HEIF（苹果 HEIC、华为 HEIF，同容器同 HEVC 编码）；**AVIF（v0.5 从「仅识别」升级为导入支持）**

> **v0.5 说明（2026-11-19）**：应用户拍板，TIFF/TIF 与 AVIF 从「小众格式 / 仅识别提示」提升为完整导入支持（Windows + Android 两端，见十章）。AVIF 的编解码无纯 Dart 实现，按 ADR-010 的原生库路子推进（Windows 随包 libavif，Android 走系统 `ImageDecoder` / `BitmapFactory`），具体选型在 M3 执行手册拆解；对齐 HEIC 的处理方式：识别出来但当前端无解码能力时报 `E-IMG-001 暂不支持该图片格式`，不能报「文件已损坏」。

> **v0.3 说明（2026-11-13）**：HEIC / HEIF 的纯 Dart 链路没有解码器，只能借平台能力——**Android 8.0+ 系统内置 HEVC 静态图解码**，走 `MethodChannel` 转 PNG 后进入既有管线；Windows 需要 HEIF 扩展 + HEVC 视频扩展（多数设备未装），鸿蒙 ImageKit 支持但排在 M4（v0.5 顺延）。因此导入能力按端开放，见十.导入表。
>
> 文件头按 ISO BMFF 的 `ftyp` box 与 brand 判定（`heic`/`heix`/`hevc`/`hevx`/`heim`/`heis`/`mif1`/`msf1` → HEIC，`avif`/`avis` → AVIF）。识别出来但当前端无解码能力时，报 `E-IMG-001 暂不支持该图片格式`，**不能**报 `E-IMG-002 文件已损坏`——照片本身是好的。

### 导出（处理完成后另存）

- 位图类：JPEG、PNG、BMP、**TIFF / TIF（v0.5 新增）**、**AVIF（v0.5 新增）**
- 图标类：ICO
- 动图类：**GIF（v0.5 新增，可导出动图，规则见边界 2）**

> **v0.5 变更**：按用户拍板，四种格式全部双向——TIFF/TIF、AVIF、GIF 加入导出列表，BMP 维持。AVIF 编码走原生库（同 ADR-010），GIF 由「仅静态取帧」升级为可导出多帧动图，规则见边界 2 与四.10。

> **v0.2 变更**：**WebP 已从导出列表移除**。`image 4.12.0` 仅提供 `webp_decoder.dart`，无任何编码器实现，纯 Dart 链路无法产出 WebP。WebP 作为导入格式完整保留（解码 → 转 PNG/JPEG 导出）。原「四.2 / 四.5 / 五.3」中 WebP 导出相关承诺同步作废，见附录 #13。

> 边界约定：
>
> 1. **SVG**：**仅渲染为位图导出，不支持矢量源码编辑、不支持导出 SVG 矢量文件**；**光栅化尺寸在导入时选择**（附录 #4 已拍板）：默认按 viewBox 推断（无 viewBox 则长边 1024），可选预设 512/1024/2048 或自定义宽高。
>    **v0.2 补充**：光栅化完成后的位图即为该次编辑会话的「原图」，二.3 的目标像素钳制上限、三.1 的 upscale 倍率均以此为基准。光栅化依赖 Flutter Engine（非纯 Dart），见七.2 例外条款与十二 ADR-004。
> 2. **APNG / GIF / 动图 WebP**：v0.2~v0.4 仅加载预览、导出静态位图；**v0.5 起 GIF 支持导出动图**（用户拍板，见四.10），APNG 与动图 WebP 仍按原规则仅导出静态帧。
>    **v0.2 补充（原缺失，必须明确）**：
>    - **导出取帧规则**：静态导出时默认取第 1 帧；若用户在预览中手动翻过帧，取用户停留的当前帧；导出确认面板需显示「将导出第 N 帧，共 M 帧」。GIF 动图导出时改为全帧写出，规则见四.10。
>    - **解码帧数上限**：`总帧数 × 单帧像素 ≤ 2 亿` 且 `帧数 ≤ 200`，超限只解前 N 帧用于预览并提示「动图过大，仅预览前 N 帧，导出的静态帧不受影响」。
>    - **动图预览策略**：预览仅解码并循环播放前 50 帧；九.3 的预览降采样对动图按**每帧独立降采样**执行。
> 3. TIFF / TIF：**v0.5 起恢复为正式支持（导入 + 导出）**，从需求池六.10 拉回，不再「已移出 MVP」（附录 #8 同步修订）。多页 TIFF 取第 1 页，导出为单页；TGA / PPM 仍留需求池六.10。
> 4. **ICO**：多尺寸容器格式，导出 UI 已定（附录 #2 已拍板）：默认勾选 16/32/48/64/128/256 全套、可取消勾选（至少保留一个），打包为单文件。
>    **v0.2 补充 3 条硬约束**（`ico_encoder.dart` 实测：内嵌 PNG 数据，`WinEncoder.encodeImages()` 对 `width > 256 || height > 256` 直接抛异常）：
>    - **尺寸上限 256**：目标尺寸超过 256 的选项在 UI 中不出现（当前默认值 256 已是库上限，无余量）。
>    - **放大置灰**：`目标尺寸 > 原图较短边` 的勾选项置灰并附文案「原图小于该尺寸，无法生成」。判据取**较短边**而非「对应边」——ICO 输出恒为正方形且按 contain 适配（见下条），缩放系数由较短边决定。禁止用 upscale 生成小图标的放大版本。
>    - **逐尺寸重采样**：ICO 打包时每个尺寸独立缩放，不沿用用户在页面顶部选定的算法。算法按尺寸分档：`<64px` 用 **average**（近似 area 盒式滤波），`≥64px` 用 **cubic**。
>      **v0.2 修订（2026-11-11）**：原写「nearest + area / lanczos」，但 `image 4.12.0` 只提供 nearest / linear / cubic / average，**无 lanczos**；分档规则保留，档内改用包内等价最优算法，不引入 FFI（维持纯 Dart 编解码铁律）。
>    **v0.2 补充 2 条 UI 边界（实现期确认，2026-11-11）**：
>    - **非正方形源按 contain 适配**：等比缩放到能装进正方形画布，居中放置，余下区域填**透明**。不变形、不裁内容（图标的标准做法）。因此横图会有上下留白。
>    - **原图较小边 < 16px 时无可用尺寸**：6 个选项全部置灰，导出按钮禁用，文案「原图较短边 N px，小于最小图标尺寸 16px，无法生成」。不静默放大。
>    **v0.4 补充（2026-11-18）：看图软件只显示一张图是正常行为，不是缺陷**
>    - ICO 是**多尺寸容器**，一个文件内嵌 N 个尺寸的图像。Windows 资源管理器、浏览器、各类看图软件打开 .ico 时**只渲染其中一帧**（通常取最大帧，或按当前缩放 / DPI 取最合适的那帧），因此「打开只看到一张图」不能作为导出失败的判据。
>    - 验证多尺寸是否真的写入，应读文件目录项而非看渲染结果：ICO 头部第 4~5 字节是帧数，之后每 16 字节一个目录项（宽、高各 1 字节，**0 表示 256**）。已用二进制解析与 PIL 双重复核：默认导出 6 帧，目录项依次为 16/32/48/64/128/256，各帧内嵌 32bpp PNG，偏移连续无缝。
>    - 另有一条易被误判的路径：**ICO 源再导出 ICO**。头部探测（`ImageHeaderProbe._probeIco`）只读目录首项，拿到的是最小尺寸；但导出实际走 `largestIcoFrame` 取像素数最大的帧，可用尺寸随之恢复，不会退化成单尺寸。已由 `encode_service_test.dart` 的「ICO 源重新打包 ICO」用例锁定。
> 5. **格式探测以文件内容为准（magic bytes），扩展名仅作提示**（v0.2 新增，原缺失）：

    | 格式 | 魔数 / 判定规则 |
    |------|----------------|
    | JPEG | `FF D8 FF` |
    | PNG | `89 50 4E 47 0D 0A 1A 0A`；再扫描 `acTL` chunk，存在则为 **APNG** |
    | GIF | `47 49 46 38`（`GIF8`） |
    | WebP | `52 49 46 46` + 偏移 8 处 `57 45 42 50`（`RIFF`…`WEBP`）；含 `VP8X` 且 flags 带 `ANIM` 位则为**动图 WebP** |
    | BMP | `42 4D` |
    | ICO | `00 00 01 00` |
    | TIFF / TIF | `49 49 2A 00`（小端）或 `4D 4D 00 2A`（大端）；大 TIFF 为 `49 49 2B 00` / `4D 4D 00 2B` |
    | AVIF / HEIC | `ftyp` box：brand `avif` / `avis` → AVIF；`heic` / `heix` / `hevc` / `hevx` / `heim` / `heis` / `mif1` / `msf1` → HEIC（两种同族，按 brand 区分，避免误判） |
    | SVG | 去 BOM 与空白后以 `<svg` 开头，或 XML 序言后首个元素为 `<svg` |

    - 扩展名与内容不一致：**以内容为准**，导入后 toast 提示一次「文件扩展名为 .jpg，实际内容为 PNG，已按 PNG 处理」。
    - 内容无法识别但扩展名在支持列表内：按「文件损坏/不支持」走九.2 错误卡片（错误码 `E-IMG-002`）。
    - **禁止**用扩展名单独判定 APNG 与 PNG（二者同为 `.png`，靠扩展名判断必然把动图当静态图并静默丢帧）。

## 二、裁剪功能

1. **载入与视图**：载入原图，画布视图自动缩放适配，**视图尺寸无需等于原图像素尺寸**；支持手势/鼠标平移、缩放浏览原图。
2. **选区形状**：正方形选区、圆形选区；**常用比例预设**（1:1、4:3、3:2、16:9）+ 自由拖拽选区 + 比例锁定。
   **v0.2 补充：形状 × 比例合法性矩阵**（原缺失，「圆形选区 + 16:9 预设」此前无定义）：

   | 形状 | 自由拖拽 | 1:1 | 4:3 | 3:2 | 16:9 |
   |------|---------|-----|-----|-----|------|
   | 矩形 | ✅ | ✅ | ✅ | ✅ | ✅ |
   | 圆形 | ✅（强制正方形） | ✅ | ❌ 置灰 | ❌ 置灰 | ❌ 置灰 |

   圆形选区本质是正方形选区 + 圆形遮罩，非 1:1 比例下列选择灰并提示「圆形选区仅支持 1:1」。「正方形选区」与「1:1 预设」为同一能力，UI 只保留一处入口（比例预设），不重复出现。
3. **手动指定选区目标像素尺寸**（例：1200×1200）：
   - 输入的目标尺寸指**原图像素尺寸**，在原图上框选对应区域。
   - 界面按当前缩放比例渲染选区框：例：原图 2400×2400 在界面显示为 200×200（缩放比 1/12）时，输入 1200×1200，屏幕上绘制的选区框实际为约 100×100。
   - **钳制规则**：输入框钳制上限为原图对应边尺寸（原图 800×800 时无法输入 1200）；拖拽选区超出图片边界时，选区自动吸附钳制到图片边界。SVG 源以光栅化后的位图尺寸为「原图尺寸」。
   - **初始定位规则（v0.2 新增，原缺失）**：输入目标尺寸后，选区以**当前选区中心为锚点**重新生成；若无选区则以**原图中心**为锚点；任一边越界时整体向内平移至贴合边界。输入即锁定选区尺寸，用户此后只有平移自由度。圆形选区时输入值为外接正方形边长。
4. **像素对齐与坐标显示**：
   - 选区坐标**吸附到整数像素**，杜绝小数像素选区导致的导出尺寸 1px 误差。
   - 界面实时显示选区对应的**原图坐标（x, y）与尺寸（宽×高）**，不受视图缩放影响。
5. **选区与视图联动**：选区定义在**原图坐标系**；视图缩放/平移仅影响显示，选区框必须跟随视图变换同步渲染，**不允许出现选区"漂移"**。
6. **透明通道**：导出 PNG 时，完整保留原图透明通道。
7. **圆形选区导出规则**：输出方形画布，圆形区域保留图像，圆形以外区域填充透明；不存在真正意义上"圆形的图片文件"，界面提示。
   **v0.2 补充**：画布边长 = 选区边长（圆形选区必为正方形）；圆形边界**启用抗锯齿**（否则边缘锯齿不可用），因此边缘 1px 过渡带内的 alpha 值会变化，验收标准见十一.1 的分项说明。

> 注：像素对齐的裁剪是**直接像素拷贝，不涉及重采样**；重采样算法选项见"三、尺寸与比例变换"。

**实现状态（2026-11-11）**：
- 选区交互已落地：`lib/core/image/crop_selection.dart`（形状/比例矩阵、平移钳制、目标像素锚定、手柄缩放）+ `crop_apply.dart`（矩形像素拷贝、圆形遮罩 + 抗锯齿）+ `crop_page.dart`（画布手势、8 手柄、比例预设）。
- 导出与编码一次完成：`EncodeRequest.crop` / `cropCircle`，在全分辨率位图上先裁后编，不产生中间文件。
- **手势分工（实现时补定，原文未写）**：选区内拖 = 平移选区，选区外拖 = 平移视图，手柄拖 = 调整大小，滚轮/双指 = 缩放。选区贴满整图时（无可移动空间）拖动降级为视图平移，避免"拖了没反应"。
- **初始选区**：导入后默认全选整图，可直接拖角缩小，也意味着"不裁也能导出"。
- **裁剪出口**：底部「下一步：导出」跳转 `/export`，裁剪参数经共享状态透传；导出面板显式显示"已裁剪 W×H"并提供「还原整图」，避免从首页直接进导出时用户不知情地丢内容。

## 三、尺寸与比例变换

1. 修改图片像素尺寸：自定义宽高；**允许放大（upscale）但有上限**——目标边长 ≤ 原图对应边 4 倍且总像素 ≤ 4000 万，超限输入框钳制并提示。SVG 源同规则，基准为光栅化后尺寸。
   **v0.2 注（2026-11-13）**：已裁剪时，上式的「原图对应边」取**裁剪选区尺寸**（导出为「先裁后缩」，缩放作用在裁剪结果上）。锁定的宽高比同样以裁剪选区为准；裁剪变更后，已设的目标尺寸按新基准重新钳制。
2. 修改图片比例，提供 3 种变换模式：
   - 拉伸填充：不保持原图比例，强制拉伸填满目标尺寸
   - 保持比例裁剪（居中裁切，cover）
   - 保持比例留白填充（contain）：空白区域填充底色（支持透明底色、自定义纯色）
3. **重采样算法**：缩放/比例变换时可选重采样算法（基础版默认高质量 **Lanczos**，进阶可加选项：双线性、最近邻等）。
   **v0.2 注（2026-11-11）**：`image 4.12.0` 无 lanczos 实现，基础版默认改用 **cubic**（包内最高质量）；真正上 lanczos 需自实现或 FFI，破坏纯 Dart 铁律，暂不引入。
   **v0.2 补充**：算法选择仅作用于「尺寸与比例变换」主操作与「转 ICO」的 ≥64px 尺寸；ICO 的小尺寸走一.4 的自动规则，不受此处影响。

**实现状态（2026-11-11）**：
- 几何与像素处理已落地：`lib/core/image/resize_geometry.dart`（4 倍边长与 4000 万像素双上限、cover 裁切区、contain 布局）+ `lib/core/image/resize_apply.dart`（三种填充模式）。
- 页面：`lib/features/resize/resize_page.dart`，宽高输入 + 比例锁 + 模式切换 + 留白底色（透明/白/黑/浅灰）+ 预览按目标比例与 `BoxFit` 渲染。
- 缩放基准由 `EditorState.resizeBase` 统一给出：裁剪生效时为选区尺寸，否则为原图尺寸；比例锁、默认目标、双上限与倍率文案共用同一基准。
- 与裁剪在同一次解码内完成，导出面板显示「已调整为 W × H」并可还原。
- 未做：重采样算法下拉（固定 cubic）、自定义取色器（当前四色预设），均记于《M1-收尾执行手册》遗留清单 L-01/L-02。

### 4.2 透明通道保留

PNG → PNG、PNG → ICO：保留透明通道。
**WebP → PNG** 同样保留 alpha（v0.2 补，原缺失）。凡目标格式不支持 alpha，均按九.4「透明填底色」处理并提示。

### 4.3 JPG 转出

JPG 本身无透明信息，仅封装转换。

### 4.4 PNG 转 JPG

透明区域自动填充底色，界面强提示：**JPG 不支持透明通道，透明区域将丢失**。

### 4.5 WebP（v0.4 已恢复导出）

- **导入支持**：WebP 可正常导入、预览、参与裁剪/尺寸变换/压缩参数预览。
- **导出支持（v0.4 起）**：Windows 随包分发 libwebp 走 FFI、Android 走系统 `Bitmap.compress(WEBP)`，两端导出面板显示 WebP 选项；鸿蒙仍不支持（见十章）。决策与代价见十二 ADR-010。
- **v0.2~v0.3 曾移除**：当时因 `image` 包无编码器整体降级为「仅导入」，v0.4 通过原生库路线恢复。旧版「导出面板不出现 WebP」「源格式降级为 PNG 并提示」两条规则**已作废**，不再执行。

### 4.6 BMP 注意事项（v0.2 新增）

BMP 技术上可通过 32bpp + BITMAPV5 头写入 alpha，但 Windows 照片查看器、主流浏览器、微信均**忽略** BMP 的 alpha 通道，透明区域显示为黑或白。因此：

- 导出 BMP 时若源图含透明，按九.4 处理（默认填白底）并提示，**不支持「透明底色 + BMP」组合**（原九.4 表述有误，已修正）。
- 界面文案避免出现「BMP 支持透明」。

### 4.7 导出前体积预估（v0.2 新增）

导出面板实时显示预估输出体积与压缩率（相对源文件）。实现方式：对降采样至长边 512 的临时图快速编码，按像素数外推，debounce 300ms。仅在预估误差可能超过 30% 时（如小体积高压缩比场景）标注「预估」。

**实现状态（2026-11-11）**：已落地。`EncodeService.estimate` 以**预览图**（导入时已生成，长边 ≤2048）为输入，无需为预估二次解码原图；再降到长边 512 采样编码，按「输出像素 / 采样像素」外推。格式、质量、色度抽样、PNG 压缩级别、调色板开关变化后均 debounce 300ms 重算；预估 < 50KB 时补一句「小体积误差较大」。ICO 不做预估——多尺寸打包体积与单一像素数不成比例，UI 直接隐藏该区块。GIF 动图导出（四.10）体积预估按首帧外推再乘帧数，标注「动图预估误差较大」。

### 4.8 AVIF（v0.5 新增，v0.5.1 修正实现方式）

- **导入**：brand `avif` / `avis` 识别为 AVIF；Windows 调随包的 libavif 官方 CLI `avifdec.exe`（静态链接、零 DLL 依赖，经 stdin/临时文件管道），Android 走系统 `ImageDecoder`（12+，低版本降级提示），解码统一转 PNG 后进入既有预览/编辑管线。像素上限由 CLI 的 `--size-limit` / 平台 `OnHeaderDecodedListener` 在分配位图前拦截。
- **导出**：Windows 调随包 `avifenc.exe` 编码，支持有损/无损（`quality=100` 为无损），默认质量 80，透明通道保留。**Android 无系统 AVIF 编码器，导出能力位关闭**（仅可导入解码）。
- **为什么用 CLI 而非 FFI 调 libavif.dll**：官方 release 只提供静态链接的命令行程序；源码自建 DLL 需 nasm/perl 且要单独分发 aom/dav1d 依赖链，与"别人无需编译环境"冲突。CLI 方案随包即开箱即用（见 windows/native/README.md）。
- **纯 Dart 铁律例外**：与 WebP / HEIC 并列，为第四处例外，须按十六章随包附 libavif / libaom / dav1d / libyuv 许可（均 BSD / RBSD）。
- **降级**：当前端无原生通道时报 `E-IMG-001`，不做静默转 PNG（避免体积暴涨且用户不知情）。

### 4.9 TIFF / TIF（v0.5 新增）

- **导入**：魔数判大小端，多页 TIFF **取第 1 页**并提示「多页 TIFF 仅编辑第 1 页」；支持 16-bit 通道降至 8-bit（沿用九.2 的量化误差约定）。
- **导出**：输出单页 TIFF（`image` 包 `TiffEncoder`），不生成多页；支持无损（默认）。透明按目标能力处理。
- **与 TGA / PPM 的边界**：本次只拉回 TIFF/TIF，TGA / PPM 仍留需求池六.10。

### 4.10 GIF 动图导出（v0.5 新增）

- **触发条件**：源为 GIF（或 APNG / 动图 WebP 在预览中翻过帧）且用户在导出面板选 GIF 为目标、勾选「导出动图」时启用；默认关闭（仍导出静态帧，保持 v0.2 行为）。
- **帧编辑范围**：仅帧序与延时（可删帧、调延时、调整播放次数），**不做逐帧内容编辑**——逐帧涂改属需求池六.1，不在 M3 范围。
- **约束**：沿用一章边界 2 的 `帧数 ≤ 200` 与 `总帧数 × 单帧像素 ≤ 2 亿` 双上限；导出帧统一尺寸（以首帧为准，其余帧按相同几何变换缩放），调色板量化到 ≤256 色。
- **合成顺序**：水印、调色、标注作用于**每一帧**；裁剪/尺寸变换统一套用同一组参数，避免帧间抖动。

## 五、图片压缩

> 本章与第四章共用导出面板，见章首说明。

1. **JPG 压缩**：可调节质量参数（1–100），有损压缩。
   **v0.2 补充**：增加「渐进式」开关（默认关，开启利于网页渐进加载）与「色度抽样」选项（4:2:0 默认 / 4:4:4 高质量）。二者均为 `image` 包 `JpegEncoder` 原生能力，几乎零成本，属 MVP 范围。
   **v0.3 修正（2026-11-11）**：「渐进式」**不可实现**——`JpegEncoder` 无 `progressive` 参数，编码器只能输出基线 JPEG（详见 ADR-006）。该项从 MVP 移除，UI 不出现该开关。**色度抽样已实现**（`JpegChromaOption`，默认 4:2:0）。
2. **PNG 压缩**：支持有损调色板压缩 / 无损压缩二选一；**检测到半透明像素（0<alpha<255）时自动禁用调色板选项并说明原因**，防止 PNG8 将半透明压成二值透明（附录 #1 已拍板）。
   **实现状态（2026-11-11）**：已落地。压缩级别 0–9（默认 6，映射 `PngEncoder(level:)`）；调色板压缩走 `quantize(256 色)` 后编码，输出带 PLTE 的索引色 PNG。半透明检测由 `alpha_scan.dart` 在导入解码阶段完成（结果存入 `DecodeResult.hasSemiTransparent`），UI 据此禁用开关；编码端另有一层兜底，直接调 API 传 `pngPalette` 也会被跳过。
3. **WebP 压缩**：**本节随 WebP 导出能力一并暂缓（附录 #13）**。导出面板无 WebP 目标，压缩参数区不出现 WebP 质量滑块。若后续引入 FFI 方案恢复导出，本节随之启用。
4. **体积预估**：见四.7。
5. **边界**：BMP 默认无压缩；ICO、SVG 不做压缩功能。
6. **一次编码原则（v0.2 新增）**：任一导出操作只允许经过一次有损编码。禁止「先转格式再压缩」的两段式实现，转换与压缩参数必须在同一次编码调用中同时生效。

## 六、文件交互

### 6.1 导入方式

- Windows：文件选择器 + 拖拽导入（拖拽时按扩展名预过滤，落地后仍按一.5 内容探测校验）
- Android / HarmonyOS Next：系统文件选择器（Android 13+ 走 **Photo Picker 免权限方案**，低版本回退传统选择器）
- 微信小程序：从相册选择

**实现状态（2026-11-11）**：Windows 拖拽已落地（`desktop_drop` 0.8.4 + 首页 `DropTarget` + 悬停遮罩）。v0.5 起多文件全部进批量队列（九.1，原「只取第一个」作废）；非图片文件直接 toast「不支持的文件类型」，不进入解码（六.5）。

**Android 导入（2026-11-11）**：`ImportService.importTypeGroup()` 同时提供 `extensions` 与 `mimeTypes`。原因是 `file_selector_android` 会把扩展名经 `MimeTypeMap` 转 MIME，转换失败的扩展名只打一条 warning 就被丢弃，`.ico` 在多数 ROM 上正属于这种——不显式给 MIME，ICO 文件在选择器里直接不可见。两侧清单都与 `PlatformCapabilities.importFormats` 同源，不手写第二份。

### 6.2 导出通道矩阵（v0.2 重写；原文「唤起系统保存面板」在移动端不成立）

> **背景**：Android / 鸿蒙不存在「系统保存对话框」这一概念。`file_selector` 仅 Windows 实现 `getSaveLocation`，移动端无对应 API。必须按端定义具体通道，否则移动端导出的实现会在开发中期才暴露。

| 端 | 导入实现 | 导出实现 | 备注 |
|----|---------|---------|------|
| Windows | `file_selector.openFile` + 拖拽 | `file_selector.getSaveLocation` → 写文件 | 系统面板自带同名冲突处理 |
| Android | `file_selector.openFile`（13+ Photo Picker） | **已定**：`flutter_file_dialog`（SAF `ACTION_CREATE_DOCUMENT`）；解析失败降级 `share_plus` | 见 ADR-007，附录 #14 已结案 |
| HarmonyOS Next | `file_selector` ohos 变体（需核对适配清单） | **已定**：暂只走 `share_plus`（无 SAF 等价物），M4 前 PoC 复核 | 插件可用性风险最高，见七.2 / ADR-007 |
| 微信小程序 | `wx.chooseMedia` | `wx.saveImageToPhotosAlbum` | V3+ |

- 移动端覆盖同名文件前弹确认。
- 导出目录不可写、磁盘空间不足、权限被拒均按九.2 错误码处理，提供「换一个位置」或「重试」。

**实现状态（2026-11-11，M2 开工）**
- **Android 导出通道已落地**：`ExportService` 按端分派，Android 走 `flutter_file_dialog` 的 `saveFile`（SAF `ACTION_CREATE_DOCUMENT`），由系统把字节写进用户选定位置；桌面端仍走 `file_selector.getSaveLocation`。MIME 由 `ImageFormat.mimeType` 提供（SAF 只认 MIME，不认扩展名）。
- **`content://` 不直接暴露给用户**：SAF 拿不到文件系统路径，`displaySavedPath` 把它统一显示为「你选择的位置」。
- **能力位如实**：`systemSavePanel` 在 Android 为 `true`（已实现），在鸿蒙为 `false`（`share_plus` 通道尚未接入，M4 落地）——避免重演 S8 那次「能力位说有、代码没有」。
- **`saveFile` 的 `content://` 解析**：插件内部已完成写入，返回 URI 仅用于展示，不需要再落地写文件，ADR-007 里「SAF 返回路径可写性」这一待 PoC 项因此不构成风险；仍需真机复核的是第三方 DocumentsProvider（网盘）下的回调行为。
- **未做**：同名覆盖确认（SAF 由系统 DocumentsUI 自带），鸿蒙通道（M4）。

### 6.3 权限适配

移动端优先 Photo Picker 免权限路线（Android 13+ / 鸿蒙对应方案），仅低版本回退传统存储权限；无网络上传动作。

### 6.4 批量约束（v0.5 重写）

v0.5 起统一为批量流水线（九.1）：所有导入入口均**支持多选**，选一张即 N=1 特例；批量只做 Windows + Android 两端（新 M3 范围）。队列按串行逐张处理，峰值内存仍受九.3 单张上限约束。批量数量上限、失败隔离与取消行为见九.1。

### 6.5 导入失败兜底（v0.2 新增，v0.5 修订）

- 拖拽多文件：**全部加入批量队列**（v0.5 起，原「只取第一个并提示一次一张」作废）；非图片文件在加入时即剔除并提示「已跳过 N 个非图片文件」。
- 拖入非图片文件：不进入解码，直接 toast「不支持的文件类型」，停留在当前页。
- 导入过程中取消：清空本次队列回到空态，不残留半解码状态；已在队列中的其它图片不受影响。

## 八、非功能需求

1. **离线优先**：所有图片解码、编辑、压缩、转换运算全部在本地运行，不请求后端上传原图。
2. **透明通道一致性**：凡是目标格式支持 Alpha 通道的，必须保证处理链路不丢失透明。
3. **内存控制**：大图（4K+、大尺寸 GIF）做采样预览，避免 OOM；移动端严格管控内存。量化阈值见九.3。
4. **性能**：裁剪、转换、压缩过程展示加载进度；**MVP 不做任务取消**（`image` 包编码不支持中断，协作式真取消移入需求池六.11，附录 #9 已拍板）。
5. **无水印**：工具本身导出图片不会自动增加额外水印。

6. **EXIF / 元数据（v0.2 重写；原「剥离全部元数据」会把色彩和 DPI 一起弄坏）**

   元数据分两类，处理策略不同：

   | 类别 | 内容 | 导出策略 |
   |------|------|---------|
   | **隐私类** | EXIF（GPS、拍摄时间、设备型号、序列号、镜头信息）、XMP、IPTC、MakerNote | **默认剥离**，定位为隐私特性并在界面注明「已移除拍摄地点与设备信息」 |
   | **渲染类** | ICC Profile（iCCP）、pHYs（DPI）、gAMA、sRGB chunk | **必须保留**，见下 |

   - 源图色彩空间非 sRGB（如 Display P3、Adobe RGB）：导出前转为 sRGB，并写入 sRGB ICC profile。目标格式不支持 ICC（BMP）时仅做像素值转换，不写 profile。
   - 源图含 pHYs：保留原始 DPI 值；无 pHYs 时不写入（不臆造 72 DPI）。
   - `image` 包 `PngEncoder` 原生支持 `_writeICCPChunk()` 与 `pixelDimensions` 参数，保留渲染类元数据零额外成本。
   - 显示与处理前应用 EXIF orientation（附录 #6 已拍板：MVP 必做）：解码后立即 `bakeOrientation`，旋转视为已烧入像素，**不得二次旋转**。

7. **反悔兜底（v0.2 变更）**：MVP 只提供「**重置 / 重新载入原图**」（回到本次会话的初始载入状态，含恢复全部参数默认值）。
   **「单步撤销」移入需求池六.8**：在「独立单任务」模型下，单页内只有一个可变参数，撤销语义与重置高度重叠；而实现需缓存一份位图快照，移动端峰值内存直接翻倍，收益远低于成本。
   **v0.5 备注**：原决策理由基于已作废的「独立单任务」模型；批量流水线（九.1）下「撤销」语义变为撤销上一步编辑操作，需求池六.8 的重新评估放在 M3 执行手册处理，本次不恢复。

8. **色深与色彩管理**（附录 #12 已拍板）：解码失败（如 CMYK JPEG）→ 按九.2 错误卡片提示「不支持该编码」（`E-IMG-003`）；可解码但降级（如 16-bit PNG 降 8-bit）→ 导入后 toast 提示一次，可继续。

9. **执行线程约束（v0.2 新增，原缺失）**

   所有解码、重采样、编码操作**必须在后台 Isolate 中执行**，主 Isolate 只负责 UI 与进度回传：

   - Windows / Android / 鸿蒙：`Isolate.run()` 或 `compute()`；大图数据进出 Isolate 使用 `TransferableTypedData` 避免内存拷贝翻倍。
   - 进度回传采用节流（≤10 次/秒），避免消息风暴。
   - 移动端编码任务串行执行，禁止并发大图任务。

## 九、交互与默认值规范

### 9.1 编辑会话模型（v0.5 重写：统一批量流水线）

> **v0.2~v0.4 的「独立单任务、一次一张」模型已作废。** 用户 2026-11-19 拍板改为统一批量流水线，本章以下规则为准。

- **唯一入口**：首页只有一个编辑入口，进入后先选图（可多选），选一张即 N=1 的特例，不再区分「单图」与「批量」两套流程。
- **流水线阶段**：选图（1~N 张）→ 统一配置（裁剪 / 尺寸 / 调色 / 水印 / 标注 / 格式与质量）→ 批量处理 → 批量导出。各阶段配置对选中**全部图片**生效。
- **参数作用域**：裁剪/尺寸因图而异（每张图单独调选区与基准），调色/水印/标注/导出参数为**全局一套**，一次配置套用全部图片；界面需分区标明「逐张调整」与「批量套用」。
- **可选项**：裁剪、尺寸、调色、水印、标注均为可选阶段，用户跳过即透传；导出为必经阶段。
- **失败隔离**：单张解码/编码失败不中断队列，记入失败清单（文件名 + 错误码），其余照常出；结束后统一展示「成功 N / 失败 M」并提供失败项重试。
- **取消**：批量处理支持中途取消（分块间检查取消标记，附录 #9 的「协作式任务取消」在 M3 随批量一并落地，不再留高阶池）。
- **内存约束**：批量不并行解码，按串行逐张「解码 → 编辑 → 编码 → 释放」推进，峰值内存不超过单张上限（九.3）；队列只持有待处理文件路径，不持有位图。
- **与旧规则的关系**：原「不支持跨功能串联」「独立单任务」「一次只处理一张」三条全部失效；四、五章「导出/压缩合并为同一面板」的规则保留，仍是同一次编码。

### 9.2 错误与边界 UX 规范

### 9.3 内存阈值（八.3 的量化）—— **v0.2 重写**

**（1）延迟渲染架构（原「既要降采样又要保留全分辨率」自相矛盾，此处定死）**

```
导入 → 解码全图 → 生成长边 ≤2048 的预览图 → 立即释放全图
     → 编辑仅操作预览图 + 参数（选区/目标尺寸均记录在「原图坐标系」）
     → 导出时：从源文件字节流重新解码全图 → 应用参数 → 编码 → 释放
```

- 编辑态只保有一份预览图（长边 ≤2048，约 16MB），参数以原图坐标系存储，缩放前后一致。
- 导出期峰值 = 全尺寸图 + 编码输出缓冲，**不含预览图**（预览图在导出开始时释放）。
- 二次解码使导出耗时增加约 40%–100%，导出进度条必须覆盖「重新解码 → 处理 → 编码」三段，文案分别为「载入原图 / 处理中 / 写入文件」。
- 源文件字节流在会话期内缓存（不重复读盘），但**不缓存已解码位图**。

**（2）分端处理上限（原统一 100MP 对移动端必 OOM）**

| 端 | 像素上限 | 依据 |
|----|---------|------|
| Windows | **100 MP** | 400MB 位图，桌面内存充足 |
| Android / HarmonyOS Next | **32 MP** | 128MB 位图，中端机 heap 512MB 留 3× 余量 |

- 超限直接拒绝（`E-IMG-004`），不做降级处理——降级会让用户拿到与原图不符的结果。
- 预检在解码前执行：仅读文件头取得宽高，不解码像素。`宽 × 高 × 4 + 编码缓冲估算` 与平台可用内存对比，不足则 `E-IMG-005`。
- **HEIC / HEIF 例外（v0.3）**：宽高在 `ispe` box 内，纯 Dart 不做 box 树遍历，改由平台侧 `inJustDecodeBounds` 先取尺寸、超限直接返回**不分配位图**，判定结果与本表一致（Android 32 MP）。
- **Dart 的 OOM 是进程级 crash，catch 不住**，因此九.2 的错误卡片只能依赖解码前预检拦截，不能依赖异常捕获兜底。

**（3）预览降采样**：原图边长 > 4096px 或总像素 > 2000 万时，预览图长边降至 2048；否则预览图 = 原图（省一次缩放）。
**（4）并发**：移动端编码任务串行执行，禁止并发大图任务。

### 9.5 页面状态机（v0.2 新增）

每个功能页共用同一套状态机，页面仅在「可编辑」态内容不同：

```
空态(未选图) --导入--> 探测中 --失败--> 错误态(E-IMG-0xx，可重新选择)
                          |
                       解码中（进度：读文件/解码/生成预览）
                          |
                       可编辑（预览图 + 参数面板 + 实时体积预估）
                          |
                  --导出--> 导出中（重新解码/处理/编码/写入）
                          |            |
                       完成态        导出失败态(E-EXPORT-0xx，可重试/换位置)
                          |
                   「继续编辑」/「完成返回首页」
```

- 任一「中」态都**不允许**用户返回上一页做别的事（微信小程序模型不支持后台任务），返回即取消并丢弃。
- 解码中/导出中都禁用所有输入控件，仅保留进度与取消关闭（关闭 = 丢弃本次结果）。

| ICO 导出 | 勾选 N 个尺寸 → 输出单文件含 N 个图标项；每项尺寸与勾选值一致；超出原图较短边的选项被置灰；**非正方形源按 contain 居中、余下区域为透明**；小于 16px 的源禁用导出 |
| 格式探测 | 将 PNG 改名为 `.jpg` 导入 → 按 PNG 处理并提示；APNG 导入 → 识别为动图、帧数正确、不丢帧 |

| 反悔兜底 | 重置后所有参数回到默认值、预览回到初始载入状态 |
| 体积预估 | 预估体积与实际导出体积偏差 ≤ 30%（20 组样本，排除 <50KB 小文件） |

**实测记录（2026-11-13，Windows）**——结案 M0「延迟渲染性能验证」：

## 十二、架构决策记录（ADR，v0.2 新增）

> 以下 8 条为本次评审与 M1/M2 推进期间拍板的重大决策，后续开发不得静默推翻；如需变更须新增 ADR 条目并回写相关章节。

### ADR-001：不支持导出 WebP，仅保留导入（**已被 ADR-010 取代**）

- **原决策**：MVP 及可见版本内不做 WebP 导出。
- **原依据**：`image 4.12.0/lib/src/formats/` 仅有 `webp_decoder.dart`，全库无 `WebPEncoder` 类；纯 Dart 生态无可用编码器。
- **被否方案**：① FFI 引入 libwebp——破纯 Dart 铁律，Windows/Android/鸿蒙三端各需编 native 库，鸿蒙风险极高；② 自研 VP8L 编码器——半年起步，不建议。
- **重开条件**：出现成熟的纯 Dart WebP 编码包，或鸿蒙 native 构建链路成熟到可承受 FFI。
- **2026-11-18 修订**：重开条件已满足——Android 有系统自带 WebP 编码器（`Bitmap.compress`），Windows 侧 libwebp 的构建与分发成本实测可控（3 个 DLL 共 1.4MB）。本条决策由 **ADR-010** 取代：WebP 导出在 Windows 与 Android 开放，其余端仍关闭。

### ADR-002：采用「延迟渲染」内存架构

- **决策**：编辑态只持有长边 ≤2048 预览图，导出时从源文件二次解码全图。
- **依据**：原「降采样预览 + 全分辨率导出」自相矛盾——保留全图则降采样无意义，丢弃全图则必须二次解码。
- **代价**：导出耗时增加 40%–100%；进度条需覆盖三段。
- **备选**：始终持有全图——32MP 需 128MB，移动端多任务场景易被系统回收，且无法支撑 100MP 桌面场景。

### ADR-003：编解码在后台 Isolate 执行

- **决策**：所有解码/重采样/编码走 `Isolate.run()`。
- **依据**：主线程解码会冻结 UI，进度条本身也会卡死。
- **注意**：跨 Isolate 传大图须用 `TransferableTypedData`，否则内存翻倍。

### ADR-004：SVG 光栅化为纯 Dart 铁律的例外之一

- **决策**：允许 `flutter_svg` + `PictureRecorder` 参与 SVG 光栅化。
- **依据**：`image` 包无 SVG 解码器，无纯 Dart 替代。
- **影响**：SVG 无法在单元测试覆盖。
- **v0.3 修正（2026-11-13）**：不再是「唯一例外」。ADR-009（HEIF 解码）同样绕开纯 Dart，两处例外均已在七.2 显式记录。

### ADR-009：HEIC / HEIF 解码走平台通道

- **决策**：Android 8.0+ 用 `BitmapFactory` 解码 HEIC/HEIF → PNG 字节 → 回到既有 Dart 管线；Windows 用随包分发的 libheif（见 ADR-010）；其余端暂不支持，能力位不开。
- **依据**：纯 Dart 生态无 HEVC 解码器；`image` 包对 HEIC 返回 null，会被误判成「文件已损坏」。用户场景真实存在——iPhone/华为默认拍照格式就是它。
- **影响**：
  - 导入时多一次平台解码（HEIC → PNG），导出前还要再解一次（全图），不缓存全图 PNG（移动端常驻 20MB+ 代价过高）。
  - 像素上限改由平台侧先判尺寸再分配位图，避免 Dart 侧 OOM（Dart 的 OOM 是进程级崩溃，catch 不住）。
  - 鸿蒙排 M4（v0.5 由 M3 顺延），当前报 `E-IMG-001 暂不支持该图片格式`。
  - **2026-11-18 修订**：Windows 原为「缺 HEVC 解码组件」，现改为随包分发 libheif + libde265（ADR-010），Windows 能力位开放。

### ADR-010：WebP 导出与 Windows HEIC 走随包原生库（第三处纯 Dart 例外）

- **决策**：
  - **WebP 导出**：Windows 用 FFI 直调随包分发的 libwebp；Android 用系统自带 `Bitmap.compress(WEBP)`；鸿蒙暂不开放。
  - **Windows HEIC 解码**：用随包分发的 libheif（内置 libde265 做 HEVC 解码）替换「让用户装商店 HEVC 扩展」的方案。
- **依据**：
  - `image` 包只有 webp 解码器、无编码器（ADR-001 的原依据），纯 Dart 路线走不通。
  - WebP 编码的现实成本被高估了：libwebp + libsharpyuv + heif 三个 DLL 合计 1.4MB，Windows 端一次构建、随包分发即可；Android 端连新增依赖都不需要。
  - Windows 侧 HEVC 解码只有两条路——装商店收费的 HEVC 扩展（多数用户没有），或自带 libheif。实测本机有 `Microsoft.HEIFImageExtension` 但**无 HEVC 解码组件**，WIC 解不了，只能自带。
- **被否方案**：
  - ① Windows 用 WIC 编码 WebP ——依赖用户装了商店的 WebP 扩展，不可控；
  - ② 鸿蒙一起做 ——鸿蒙 native 构建链尚未验证（M4），贸然引入 FFI 风险不可控，等环境就绪再评估。
- **影响**：
  - 七.2「纯 Dart 铁律」出现**第三处例外**，需显式记录；
  - 原生库随 exe 分发（`windows/native/bin/x64`），CMake 负责安装到 exe 同目录；
  - Windows WebP 编码在编码子 Isolate 内经 FFI 完成，不经平台通道——桌面 embedder 不支持后台 isolate 发平台消息，通道方案在 Windows 不可用；
  - Android WebP 编码走平台通道，但需 `BackgroundIsolateBinaryMessenger`（Android 支持后台 isolate 发平台消息）；
  - libheif 为 LGPL-3.0、libde265 为 LGPL-3.0、libwebp 为 BSD-3，均可随包分发；HEVC 专利由用户设备自带的解码实现承担，libde265 只做解码不做编码。
- **重开条件**：若出现成熟的纯 Dart WebP 编码包，优先回退到纯 Dart 实现。

### ADR-005：元数据分级剥离

- **决策**：剥隐私类（EXIF/GPS/XMP/IPTC），留渲染类（ICC/pHYs/gAMA/sRGB）。
- **依据**：全剥会导致 P3 照片偏色、打印 DPI 错乱，且与八.8 色彩管理自相矛盾。
- **代价**：需实现非 sRGB → sRGB 的像素转换（`image` 包有 `ColorProfile` 基础能力，需验证）。

### ADR-006：渐进式 JPEG 不实现

- **决策**：MVP 不提供「渐进式」导出开关，UI 不出现该选项。
- **依据**：`image 4.8.0` 的 `JpegEncoder.encode` 只有 `chroma` 与 `singleFrame` 两个参数，构造器只有 `quality`；全库检索 `progressive` 仅命中解码侧的 `JpegData` / `JpegFrame` / `JpegScan`（读取 SOF2 标记），编码器始终输出基线 JPEG。PRD 五.1 原文「二者均为 `JpegEncoder` 原生能力」对渐进式不成立。
- **影响**：需要渐进式时只能自实现 progressive scan 或引入原生库，违反「纯 Dart 编解码」；转入需求池，待有 FFI 方案再评估。

### ADR-007：移动端导出通道选型（附录 #14 结案）

- **决策**：
  1. **Android 主通道** = `flutter_file_dialog` 的 `saveFile`（底层 SAF `ACTION_CREATE_DOCUMENT`）。
  2. **兜底通道** = `share_plus` 分享缓存文件（写 `<cache>/export/` 后 `shareXFiles`）。
  3. **鸿蒙 MVP 通道** = 仅 `share_plus`（无 SAF 等价物，见下方风险）。
  4. **否决 MediaStore**。
- **依据**：
  - **`file_selector` 无解**：`file_selector_platform_interface 2.7.0` 的 `getSaveLocation` 默认实现回落到 `getSavePath`，后者直接 `throw UnimplementedError`。即任何平台包不覆写就没有保存面板——这从源码层面确认了六.2 的判断，移动端不能指望 `file_selector`。
  - **SAF 是唯一与桌面语义对齐的方案**：用户自选目录、系统面板自带同名冲突处理、返回可写目标，UI 与错误处理可与 Windows 完全复用（`ExportService.save` 一行平台分支即可）。且 SAF **不需要任何运行时存储权限**——权限面最小，与「离线 + 最小权限」的定位一致。
  - **`share_plus` 只做兜底，不做主通道**：它把"保存"变成"分享"，用户要多点一次并自己选目标应用；对「另存为 xxx.png」这种明确诉求是体验倒退。但它的覆盖面最广（三端行为一致、无需权限、写的是应用私有缓存），因此保留为 SAF 不可用时的降级路径。
  - **否决 MediaStore**：① 只能落进图片集合，`.ico` / `.bmp` 不在其 MIME 白名单，等于给导出格式加了一条隐形限制；② 语义是"存进相册"而非"存成文件"，用户拿不到自己想要的文件名与目录；③ API ≤28 仍需 `WRITE_EXTERNAL_STORAGE`，29+ 虽免权限但老设备要额外分支，权限面反而比 SAF 更大。
- **代价与风险**：
  - `flutter_file_dialog` 在 Android 上把 SAF 返回的 `content://` 解析成本地路径，对部分第三方 provider（网盘类）可能拿不到真实路径 → 解析失败时自动降级到 `share_plus`，并提示「已改为分享方式导出」。
  - **鸿蒙是最大不确定项**：`flutter_file_dialog` 无 ohos 变体，`share_plus` 的 ohos 支持也需实测。M4 开工前必须先做 PoC（见下方清单），PoC 不过则鸿蒙导出只能退到「保存到应用沙箱 + 提示用户用文件管理器取」，体验明显降级，需产品确认。
- **待 PoC 验证项（M2 前完成，结论回写本节）**：
  1. `flutter_file_dialog` 在 Android 10 / 13 / 15 上返回的路径可否直接 `writeAsBytes`；
  2. 从 Google Drive / 系统「最近」等 provider 选目录时的解析行为；
  3. 同名文件覆盖行为是否与六.2「覆盖前弹确认」一致（系统面板可能已自带，则我方不再弹）；
  4. 鸿蒙上 `share_plus` 的 `shareXFiles` 是否可用、落到哪个系统入口；
  5. 大文件（20MB+）走 SAF 与走 share 缓存的耗时差异。
- **影响**：六.2 导出通道矩阵、附录 #14 已同步结案；`ExportService.save` 需要在 M2 增加「通道选择」分支（`ExportChannel { savePanel, safDocument, shareSheet }`），`file_io_native.dart` 之外新增 `export_channel_android.dart` / `_ohos.dart` 条件实现。

### ADR-008：SVG 光栅化 PoC 结论 —— MVP 仍不接入（M0 结案）

- **决策**：十章 SVG 行维持全端 ❌，`PlatformCapabilities.importFormats` 继续排除 SVG。M0「SVG 光栅化 PoC」按此结论结案。
- **依据（`flutter_svg 2.3.2` 实测，2026-11-13）**：

  | 特性 | 实测 | 判定 |
  |------|------|------|
  | 实心矩形 / 线性渐变 | 渐变产生 284 种颜色 | ✅ |
  | 圆外透明 | 非透明像素 8409/16384，与 πr² 相符 | ✅ |
  | `clipPath` | 与不使用 clip 的圆形结果**逐项相同**（8409 像素 / 114 色） | ✅ |
  | `mask` | 非透明像素恰为一半（8192/16384） | ✅ |
  | `path` + `transform` | 2747 像素 / 96 色 | ✅ |
  | **`feGaussianBlur`** | 加与不加 filter **输出完全相同**（384 B / 6084 像素 / 3 色） | ❌ **静默忽略** |
  | `text` | 单色块（测试环境无真实字体，回落到方块） | ⚠️ 依赖字体 |
  | 1024×1024 光栅化 | 59 ms | ✅ 可接受 |

  **决定性理由是 filter 静默失效**：设计稿里的投影、模糊、发光经 `flutter_svg` 渲染后直接消失，既不报错也不提示，用户只会觉得「导出的图和原来不一样」。这比不支持 SVG 更糟——不支持时用户明确知道进不来，支持一半会让用户以为能用。

- **对 ADR-004 的修正**：ADR-004 写「SVG 无法在单元测试覆盖」，**该前提不成立**。`vg.loadPicture(SvgStringLoader(...), null)` + `Picture.toImage` 在 `flutter test` 里可直接跑，配合 `toByteData(rawRgba)` 能做逐像素断言（本次 PoC 即全部在单元测试内完成，含 1024px 光栅化 59 ms）。将来接入 SVG 时，渲染正确性可以被自动化覆盖，不需要「只能靠人眼」。
- **将来接入的前提条件**：
  1. 在 UI 上明确声明不支持 filter 类效果，或接入前自实现一遍 filter；
  2. `text` 用系统字体渲染会导致跨平台字形不一致，需明确是否支持文本类 SVG，或提示「文本可能显示不一致」；
  3. 用 `flutter build windows --analyze-size` 实测包体增量，对照十四章「Windows ≤ 40 MB」与「超预算优先砍 SVG」的既定顺序。
- **影响**：十章 SVG 行的 v0.3 修订（改 ❌）无需回滚；M0 五项全部结案。

## 十三、页面清单与导航结构（v0.2 新增）

图片格式工厂
├── 首页 /（v0.5 统一为单一「开始编辑」入口）

├── 兼容旧路由（v0.5 保留别名，指向 /pipeline 对应阶段）

    ├── 错误卡片 / 失败清单（页内组件，非独立路由）

> **入口数量说明（v0.5 修订）**：首页由「4 入口 / 3 页面」收敛为**单一「开始编辑」入口**——选图后进入 `/pipeline`，单图即 N=1。裁剪/尺寸/调色/水印/标注/导出是流水线内的**阶段**而非并列入口，参数一次配置、对全队列生效（九.1）。旧路由 `/crop` / `/resize` / `/export` 保留为别名以兼容既有深链与用例，界面不再单独暴露。

**导航规则（v0.5 重写）**：

- 首页 → `/pipeline`：选图（1~N 张）后 `push`；阶段之间为流水线内前进/后退，不回首页。
- 逐张调整阶段可按队列切到下一张；批量套用阶段一次配置作用于全部图片，界面分区标明作用域（九.1）。

## 十四、性能预算（v0.2 新增）

见十一.2 的具体数值表。补充约束：

1. **启动预算**：首帧 ≤ 800ms（Windows）/ 1.5s（移动端）；首页不预加载任何图片库资源，`image` 包按需 import，避免拖慢冷启动。
2. **包体预算**：Windows ≤ 40MB、Android ≤ 25MB、鸿蒙 ≤ 25MB。超预算时优先砍 SVG 光栅化（`flutter_svg` 体积较大）而不是砍功能。
3. **内存预算**：见十一.2；移动端以「系统不触发 LMK 回收」为红线，预检时必须查询可用内存而非固定阈值。
4. **无卡顿红线**：任何用户操作后 100ms 内必须有视觉反馈（哪怕只是 loading 态）。
5. **测量方式**：Windows 用 DevTools Memory + 手工计时；Android 用 `dumpsys meminfo` + Android Studio Profiler；鸿蒙用 DevEco Profiler。数据记入验收报告。

## 七、动图合成与视频转换类（v0.8 入池，2026-11-24 用户拍板，尚未排期）

> 与四.10 的边界：四.10 是**单个已有动图 → 同格式重导出**（保留帧序/延时/循环）；本章是**从零生成动图**——来源是多张静态图或视频，目标是新的动图文件。两者入口不同，勿混。
>
> 可行性口径：只回答「技术上能不能实现」，✅ = 有现成或成熟的纯 Dart / 随包原生能力，⚠️ = 可实现但要新写编码器或引入原生库（成本较高），❌ = 三端均无可行路径。鸿蒙按 M4 评估口径，Android 按「系统无编码器则须随包原生库」口径。

**1. 多图合成一张动图**（N 张静态图按选定顺序合成为 1 个动图文件，统一帧尺寸，可设帧延时与循环次数）

| 目标格式 | Windows | Android | 鸿蒙（M4） | 状态 | 实现要点 |
|---|---|---|---|---|---|
| GIF | ✅ 可实现 | ✅ 可实现 | ✅ 可实现 | ⏸ | `FormatEncoders.encodeGif` 已具备多帧编码能力，缺的是帧序列数据模型与合成入口；GIF 256 色量化、各帧统一尺寸（以首帧为准） |

| WebP 动图 | ⚠️ 可实现，成本高 | ⚠️ 可实现，成本高 | ⚠️ 可实现，成本高 | ⏸ | **生态兼容性好**，是动图路线中优先级最高的目标格式；视频抽帧 + 上表 WebP 动画编码，两段能力都要补 |
| APNG 无损动图 | ⚠️ 可实现，成本高 | ⚠️ 可实现，成本高 | ⚠️ 可实现，成本高 | ⏸ | 画质上限高于 WebP 动图，但只能无损、体积大很多且社交平台支持很差；视频抽帧 + 上表 APNG 编码；注意视频帧本身有损，无损容器不等于无损画质 |
| AVIF 动图 | ⚠️ 可实现，成本高 | ⚠️ 可实现，成本高 | ⚠️ 可实现，成本高 | ⏸ | **压缩更强但生态兼容性差**，国内社交平台基本不支持，优先级最低；视频抽帧 + 上表 AVIF 动画编码；Android 与鸿蒙均无现成编码端 |

> **共同技术障碍**：① 视频解码依赖会显著推高包体积，与「纯本地离线小工具」定位有张力；② 各帧必须统一尺寸，涉及等比缩放 + 居中裁切/留白，需复用 `computeResizeGeometry` 保证与像素变换一致；③ 帧数上限与内存预算须按九.3 约束，防止长视频抽帧 OOM；④ WebP / AVIF 动画编码在三端都无现成能力，是这两条路线的主要成本来源。
>
> **生态兼容性（2026-11-24 用户补充）**：动图 WebP 在互联网大量使用、兼容性很好，是动图路线中价值最高、应优先落地的目标格式。APNG 画质上限比 WebP 动图高，但只能无损、体积普遍比动图 WebP 大很多，且社交平台支持很差，只适合追求画质的本地用途。动图 AVIF 压缩更强，但属小众前沿、兼容性坑非常多，**国内社交平台基本不支持动图 AVIF**，即使产出来也难以分享，故优先级最低。WebP 与 AVIF 都需要新写编码能力，成本相近，但收益差距明显；APNG 虽是纯 Dart 可解、实现成本最低，但分享场景受限，不是通用首选。
>
> **建议排期顺序**：多图 → GIF（可复用现成编码器，改动最小）→ 多图 → WebP 动图（生态兼容性好，价值最高）→ 多图 → APNG（纯 Dart、实现成本最低，但只适合本地画质用途，分享场景受限）→ 视频转 GIF/WebP/APNG → 多图 → AVIF 动图（生态兼容性差，押后）→ 视频转 AVIF。

### 3. 裸眼 3D 九宫格（版本 A：8 背景 + 中间镂空 + 人像跨白线）

> 区分两个容易混淆的版本：**版本 A（本需求，主流爆款）** = 8 张背景 + 中间镂空 + 人像跨白线，有冲出 3D 感；**版本 B（简单版）** = 9 张图、中间一张圆形抠图人像、不压白线，只有圆形头像效果，没有立体感。本次只做 A，B 不在需求内。

**App 内的制作流程**：

1. **选背景图**：可以是同一张背景重复，也可以 8 张不同图。3×3 九宫格**第 2 行第 2 列（中间格）先不画**，只画剩下 8 格，格子之间保留朋友圈原生白色间隙（gap 白线）。
2. **中间区域镂空**：整张画布是一张完整大图，8 格画好后把中间那格位置清空（透明）。
3. **导入人像并抠图**：人像放在**底层**，从中间镂空透出来；关键——人像的上半部分 / 左右部分要画到九宫格白线的**上层、盖住白线**，制造"穿出来"的层次感。即一部分人像在九宫格图层下方（在格子里），一部分在上方（压在缝隙白线上）。**这一步是立体感来源**；只做单纯叠图、没有跨白线，就没有裸眼 3D 感。
4. **加细节（加分项）**：人像边缘羽化、轻微阴影；背景可统一模糊以突出人像。
5. **切成 9 张**：把合成好的大图均等切成 9 张正方形，导出 `01.jpg` ~ `09.jpg`，用户发朋友圈按顺序勾选。8 块背景正常拼接、中间是跨白线的人像，视觉上像人像冲破九宫格。

**抠图方案（用户 2026-11-25 询问三选一，结论如下）**：

| 端 | 方案 | 可行性 | 依据与代价 |

## ✅ 已结案：#14 移动端导出通道

**原问题**：Android / 鸿蒙没有「系统保存面板」，`file_selector` 在移动端拿不到保存位置，需在三条候选里选一条。

**结论（ADR-007，2026-11-11）**：

| 端 | 选定通道 | 关键理由 |
|----|---------|---------|
| Android | `flutter_file_dialog`（SAF `ACTION_CREATE_DOCUMENT`） | 唯一与桌面「另存为」语义对齐；无需运行时存储权限；UI/错误处理可与 Windows 复用 |
| Android 兜底 | `share_plus`（写缓存后分享） | SAF 返回的 `content://` 解析不出本地路径时降级，覆盖面最广 |
| HarmonyOS Next | 暂只用 `share_plus` | 无 SAF 等价物，`flutter_file_dialog` 无 ohos 变体；M4 前 PoC 复核 |
| 否决 | MediaStore | 只覆盖图片集合（`.ico`/`.bmp` 不在 MIME 白名单）、语义是「存相册」、老设备仍需存储权限 |

**源码级依据**：`file_selector_platform_interface 2.7.0` 的 `getSaveLocation` 默认实现回落到 `getSavePath`，后者 `throw UnimplementedError` —— 平台包不覆写就没有保存面板，六.2 的判断成立。

**遗留**：五条 PoC 验证项（路径可写性、第三方 provider 解析、同名覆盖、鸿蒙 `shareXFiles`、大文件耗时）列入 ADR-007，M2 开工前完成并回写结论。
